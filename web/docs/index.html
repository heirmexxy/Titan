Titan Integration Guide

The Titan API connects your systems to the devices you own, and to the sites other organisations have shared with you. It gives you readings, alerts and condition history; lets owners send commands to their devices; and carries carbon calculations back to the signed readings and lab results they came from.

It's the same API for everyone. A warehouse platform, a lender, a solar company and a carbon verifier each see only what their own key, and any data grants they hold, allow.

Base URL: https://titan.kitovu.com.ng/v1. All responses are JSON. Times are ISO 8601 in UTC.

Authentication

Send your API key as a bearer token on every request. Keys are issued by Kitovu from the Titan admin panel and are shown once.

curl https://titan.kitovu.com.ng/v1/sites \
  -H "Authorization: Bearer tk_live_…"

Each key carries scopes:

ScopeAllows
read:readingsLatest readings, history, condition reports and proofs
read:alertsListing alerts
manage:webhooksCreating and deleting webhook subscriptions
manage:grantsSharing your own sites with other organisations
control:devicesSending commands to your own devices
read:carbonReading carbon projects, batches and results you own or can see through a grant
write:carbonRecording batches, periods and lab results on your own projects

Integration examples

Four common integrations. Each uses only the endpoints documented below.

A. Warehouse receipts (how StorageX uses Titan)

Show the condition of the stock behind each warehouse receipt.

1. Link the IDs once.

When a warehouse is set up in Titan, its StorageX warehouse ID is saved as the site's external ID, and each StorageX lot ID is saved on the matching stack. Device channels name the zone and stack, for example z1/stack-a/mst1.

2. Find the Titan site for a warehouse.

GET /v1/sites?ref=SX-WH-001

3. Subscribe to alerts.

POST /v1/webhooks
{ "url": "https://storagex.kitovu.com.ng/hooks/titan", "events": ["alert.*", "device.offline"] }

When an alert opens on a stack, flag the lots and receipts stored there. Store the returned secret to verify each delivery.

4. Attach a condition report to a receipt.

GET /v1/sites/{siteId}/conditions?lot=LOT-2026-114&from=2026-10-01T00:00:00Z&to=2026-11-13T00:00:00Z

Use the receipt's storage period as from and to. Show lenders the min, max and average for each reading, the alerts during the period, data completeness, and whether moisture went above the crop's safe level.

5. Show live conditions.

GET /v1/latest?site={siteId}

B. A lender or insurer watching financed assets

The asset owner grants the lender access to the financed sites, chosen readings and the loan period (grants). The lender's key then reads /v1/sites, /v1/latest, /v1/readings and condition reports for those sites only, and can subscribe to alert.* and device.offline webhooks. Proofs let the lender verify readings independently.

C. Solar and pay-as-you-go appliances

The company's own platform reads usage (solar.energy, equipment.runtime, appliance.door_opens, location) and locks or unlocks units when payments arrive:

POST /v1/devices/PG-000123/commands
{ "command": "paygo.unlock", "args": { "until": 1767225600 } }

The same data, shared through a grant, backs receivables financing.

D. A carbon verifier

The project owner grants the verifier access to the project's sites. With read:carbon, the verifier reads every batch or period, its calculation, the lab results (with certificate fingerprints) and the range of signed device messages each number came from, then spot-checks them with proofs.

Reading history

GET/v1/readingsread:readings
ParameterMeaning
site or deviceLimit to one site or device. Without either, all visible sites.
metricOne or more metric keys, comma separated, e.g. air.temperature,produce.moisture
channelOne channel, e.g. z1/stack-a/mst1
from, toDefault: the last 24 hours. Up to 366 days.
intervalraw (default), 1m, 1h or 1d. Aggregates return avg, min, max and count.

Raw readings carry labels you should respect:

FieldMeaning
qualityok, suspect or fault as reported by the device. Out-of-range values are never returned.
bufferedTaken during a connection outage and sent later, with the original time
timeEstimatedThe device clock was not set; Titan estimated the time
derivedCalculated by Titan (dew point, equilibrium moisture, VPD)
integritydevice-signed (Ed25519), shared-secret (approved third-party devices), or derived
seqThe device message number; use it to fetch a proof

Reading proofs

GET/v1/readings/proof?device={id}&seq={seq}read:readings

Returns the original signed message, the device's public key and Titan's own check. Anyone can verify it independently:

import { createPublicKey, verify } from 'node:crypto';
const raw = Buffer.from(proof.publicKey, 'base64url');                      // 32-byte Ed25519 key
const key = createPublicKey({ key: Buffer.concat([Buffer.from('302a300506032b6570032100', 'hex'), raw]), format: 'der', type: 'spki' });
const ok = verify(null, Buffer.from(proof.payload, 'base64url'), key, Buffer.from(proof.signature, 'base64url'));

Deliveries

Titan POSTs { "event", "created_at", "data" } with headers X-Titan-Event and X-Titan-Signature: t=<unix>,v1=<hex>. Reply with any 2xx within 10 seconds. Failed deliveries are retried 5 more times over about 30 minutes.

import { createHmac, timingSafeEqual } from 'node:crypto';
function verifyTitan(rawBody, header, secret) {
  const { t, v1 } = Object.fromEntries(header.split(',').map((p) => p.split('=')));
  if (Math.abs(Date.now() / 1000 - Number(t)) > 300) return false;          // reject old deliveries
  const expected = createHmac('sha256', secret).update(`${t}.${rawBody}`).digest('hex');
  return timingSafeEqual(Buffer.from(expected), Buffer.from(v1));
}

Sharing data (grants)

The owner of a site decides who else can see it. A grant names the organisation, the sites, the readings and the period. Grants can be revoked at any time and every read is logged.

POST/v1/grantsmanage:grants
{ "granteeOrgId": "…", "siteIds": ["…"], "metrics": ["produce.moisture", "air.humidity", "air.temperature"],
  "validFrom": "2026-11-01T00:00:00Z", "validTo": "2027-05-01T00:00:00Z", "live": true }

Leave siteIds or metrics out to share all. live lets the grantee receive webhooks for those sites.

GET/v1/grants

Grants you have given and received.

DELETE/v1/grants/{id}

Device commands

Owners can send commands to their own devices. Each device type lists the commands it accepts and who may send them; the built-in ones are alarm_ack, send_state, time_sync and reboot (the last two from the dashboard only).

GET/v1/devices/{id}/commandscontrol:devices

Commands this device accepts, with their arguments, and the recent command log (who sent what, and whether the device confirmed it).

POST/v1/devices/{id}/commandscontrol:devices
{ "command": "relay.set", "args": { "channel": "fan1", "on": true } }
→ 202 { "command": { "id": "c_3f9a…", "name": "relay.set", "args": { … }, "status": "sent" } }

Status becomes acked when the device confirms, or failed with its reason. Automations (set up in the Titan dashboard) send commands from readings automatically, and are logged the same way.

Firmware updates

Upload a firmware binary for one device type, then roll it out. Titan signs it, sends it to devices in batches while they are online, and tracks each device until it reports the new version. How devices handle updates is in Device Protocol §15.

GET/v1/firmwaremanage:firmware

Your releases, Kitovu's releases for your device types, rollouts with progress, and Titan's public signing key.

POST/v1/firmware?type=wareguard-v1&version=2.1.0&notes=…manage:firmware

Body: the raw .bin (Content-Type: application/octet-stream, up to 8 MB). Returns the release with its sha256 and signature.

POST/v1/firmware/{releaseId}/rolloutsmanage:firmware
{ "siteId": "…", "deviceIds": ["AFF-000001", "AFF-000002"], "batchSize": 10 }
→ 201 { "rollout": { "id": "…", "status": "active" }, "devices": 2 }
GET/v1/firmware/rollouts/{id}manage:firmware

Each device's state: queued, sent, downloading, installed or failed (with the reason). Pause, resume or cancel with POST …/rollouts/{id}/pause|resume|cancel.

Pay-as-you-go (PAYG)

For appliance makers and distributors: every payment buys time. Titan unlocks the appliance until the paid-up date, which the appliance enforces itself when offline, and locks it when credit and grace run out. Lease-to-own plans unlock for good once paid in full.

POST/v1/payg/plansmanage:payg
{ "name": "Solar fridge 12 months", "pricePerDay": 500, "totalPrice": 180000, "graceHours": 24, "currency": "NGN" }
POST/v1/payg/accountsmanage:payg
{ "deviceId": "KB-000123", "planId": "…", "customerName": "Adaeze Okafor", "customerPhone": "+2348031234567", "customerRef": "CUST-8812" }
→ 201 { "account": { "id": "…", "code": "KB7F3Q", … }, "payUrl": "https://titan.kitovu.com.ng/pay/KB7F3Q" }
POST/v1/payg/accounts/{id or code}/paymentsmanage:payg
{ "amount": 1500, "reference": "MOMO-55120931" }
→ 201 { "duplicate": false, "account": { "credit_until": "2026-11-22T09:14:00Z", "status": "active" } }

Post each payment from your collection system (mobile money, USSD, agents). Each reference is recorded once, so retrying is safe (repeat answers 200 with duplicate: true). Customers can also pay by card, transfer or USSD on the account's pay page; for that, Kitovu sets up a Paystack subaccount so the money settles to you.

GET/v1/payg/accounts?status=active&due=1manage:payg

Webhook events: payg.payment, payg.unlocked, payg.locked, payg.paid_off (or payg.*). Customers with a phone number get an SMS a day before credit ends.

Carbon projects

A project turns device readings and lab results into tCO₂e using a versioned method: biochar-v1 (per batch) or cookstove-v1 (per reporting period). Results keep their inputs: the signed message range for each device reading, and each lab result with its certificate fingerprint.

These are Titan's estimators. Align the project parameters with your registry methodology and validation body before issuing credits.

GET/v1/carbon/projectsread:carbon
GET/v1/carbon/projects/{id}read:carbon

Project, parameters, totals and its batches or periods.

GET/v1/carbon/activities/{id}read:carbon
POST/v1/carbon/projects/{id}/activitieswrite:carbon
{ "reference": "2026-11", "startedAt": "2026-11-01T00:00:00Z", "endedAt": "2026-12-01T00:00:00Z" }

Kiln nodes open and close biochar batches themselves with their start/end buttons; use this for periods and for kilns without a node.

POST/v1/carbon/activities/{id}/closewrite:carbon
POST/v1/carbon/activities/{id}/measurementswrite:carbon
{ "kind": "lab.organic_carbon_pct", "value": 78, "documentRef": "SGS-0042.pdf", "documentSha256": "9f2c…" }

Kinds: biochar.mass_kg, biochar.moisture_pct, feedstock.mass_kg, lab.organic_carbon_pct, lab.h_corg. Measurements are never edited; send a new one with supersedesId to correct a value.

POST/v1/carbon/activities/{id}/calculatewrite:carbon

Result status is ok, incomplete (lists what's missing) or ineligible (for biochar: H/Corg above the limit, or held temperature below 350 °C).

Verification and registries

Owners give an independent verifier (VVB) access to one project at a time from the Titan dashboard. The verifier signs in at /verify, sees the evidence (calculations, lab results with file fingerprints, and the signed device messages behind each reading), raises findings and signs a statement tied to the exact evidence fingerprint.

Verifier API. Verifiers create keys in their portal (scope verify:carbon) for their own tools:

GET/v1/verification/projectsverify:carbon
GET/v1/verification/projects/{id}?activities=…verify:carbon
POST/v1/verification/projects/{id}/findingsverify:carbon
{ "kind": "corrective_action", "activityId": "…", "text": "Lab certificate for batch B-014 is missing." }
POST/v1/verification/projects/{id}/statementsverify:carbon
{ "activityIds": ["…"], "opinion": "positive", "verifiedTco2e": 41.2, "statement": "Reasonable assurance …" }

A positive opinion is refused while corrective action requests are open, and the verified amount can't exceed what was calculated.

Owner side. GET /v1/carbon/projects/{id}/verification lists verifiers, findings, statements and submissions. Answer findings with POST /v1/carbon/findings/{id}/respond.

POST/v1/carbon/projects/{id}/submissionswrite:carbon
{ "registry": "puro", "statementId": "…" }

Registries: verra, gold_standard, puro, isometric, other. Download the package with GET /v1/carbon/submissions/{id}/package (zip: package.json, activities.csv, measurements.csv, findings.csv, README) or ?format=json, upload it through the registry's own portal, then record progress with POST /v1/carbon/submissions/{id}/status (submitted, under_review, issued with amount and serial numbers, or rejected).

Registries do not offer public submission APIs, so Titan prepares, fingerprints and tracks the submission rather than sending it. If the evidence changes after a verifier signs, the fingerprints stop matching and Titan refuses to prepare a submission from that statement.

CSV and Excel export

GET/v1/export/{dataset}?format=xlsx&from=&to=&site=&device=&metric=&interval=1hexport:data

Datasets: readings, alerts, devices, quality-tests, lots, custody, payg-payments, payg-accounts, carbon-activities. Format csv (default) or xlsx. For readings, interval is raw, 1m, 1h or 1d. AI agents (MCP)

Titan is also a Model Context Protocol server, so AI agents and assistants can read your data and, if you allow it, operate your devices.

URL:    https://titan.kitovu.com.ng/mcp
Header: Authorization: Bearer tk_live_…

The agent gets exactly the access of the key you give it: the same sites, grants, scopes, rate limits and audit trail. Tools: list_sites, get_site, latest_readings, query_readings, condition_report, list_alerts, list_devices, list_metrics, carbon_projects, carbon_project, carbon_activity, and, only for keys with control:devices, device_commands and send_command.

Give agents read-only keys unless they truly need to switch equipment. send_command is marked as an action that changes the physical world, so well-behaved clients ask the user before calling it.

Service status

GET https://titan.kitovu.com.ng/healthz/deep answers 200 when Titan, its database, workers and MQTT broker are healthy and 503 when not, with the name of each check. Point your own uptime monitor at it.

Errors and limits

Errors return { "error": "code", "message": "…" } with the matching HTTP status: 400 bad request, 401 missing or invalid key, 403 missing scope, 404 not found or not visible to you, 429 rate limited.

Each key may make 600 requests per minute. For live data, use webhooks rather than polling.
